# Protocol family: `glorious` (Glorious Model O, D and I mice)

Status: **detection only.** UDB recognises 23 Glorious mouse models (42 product
IDs across VIDs `093A`, `258A`, `22D4`, `320F` and `3794`) and sends them
nothing.

## Three generations, three protocols

| Generation | VID | Models | Wire format (per OpenMouse) |
|---|---|---|---|
| Pixart firmware | `093A` | Model O 2 / O 2 Mini / D 2 / D- 2 / I 2 | a 256-byte settings payload sent as four 64-byte feature reports, report ID `03`, on interface 1; `04 FB` settings and `02 FB` lighting; the firmware never echoes settings back |
| Classic | `258A`, `22D4`, `320F`, `3794` | Model O, D, O-, D-, I, O 2 PRO, Series 2 PRO, O Pro, Series One Pro, D 2 PRO, O V2, I 2, O3 | the format Glorious CORE speaks; write-only for settings; battery read with class `02`, subclass `02`, command `83` |
| 4K/8K (core2) | `258A` | Model O 2 PRO 4K/8K, D 2 PRO 4K/8K | unnumbered 64-byte feature reports on usage page `FFFF`, usage 0: `00 00 02 len bank register data…`, bank 0 system, 1 per-profile settings, 2 per-profile lighting; a reply echoes the request with status `A1` in byte 0 |

On the 4K/8K mice, the only reads known are the firmware (bank 0, register
`81`) and the battery (register `83`). CORE never reads a setting. The mouse
keeps three profiles, every setting write carries a profile number, and the
mouse cannot report which profile is active.

The 4K/8K frames come from a community USBPcap capture of CORE (2026-10-08)
plus names from CORE's own code. OpenMouse's note says that driver "has not run
on hardware." Wired the mouse polls up to 8000 Hz, through its receiver up to
4000 Hz.

## Uncertain entries

- `258A:2011` and `258A:2012`: OpenMouse's sources disagree on whether `2011`
  is Model O or Model D. The registry follows OpenMouse's choice.
- `320F:823A`, `320F:821A`, `320F:831A`: OpenMouse found a unit on VID `320F`
  whose feature report is 263 bytes, not 64. Its classic payloads wrote without
  error and did nothing. These three are marked unconfirmed in the entries.
- `258A:201C` and `258A:2036` (D 2 PRO 4K/8K): OpenMouse reasons from CORE's
  code that its frames are identical to the O 2 PRO 4K/8K's; no capture.
- `258A` is shared with other Sinowealth-based mice, and `093A` with Incott's;
  the entries match on VID and PID together.

## Why there is no adapter

- **Nothing can be read back.** No Glorious setting has a known read, so none
  could reach `write-verified`.
- **The active profile is unknowable.** A write lands in the profile number the
  host chose; the mouse can't confirm it is the one in use.
- **Three protocols, little hardware evidence.** The only capture is of a wired
  O 2 PRO 4K/8K, and it was taken from CORE, not from a browser.
- **The collections are known for one model only.** For the 4K/8K mice the
  config channel is the `FFFF:0000` collection with an unnumbered feature
  report; interface 1 has another `FFFF` collection (usage 1) that takes none.

## What would unblock it

1. A device report (`Copy device report`) from a Glorious mouse.
2. A read-only start: firmware and battery on the 4K/8K frame. They are the only
   known reads, but they would be `read-verified` features, not settings.
3. A way to find out which profile is active, or a UI that makes the profile
   explicit and says writes are not confirmed.
