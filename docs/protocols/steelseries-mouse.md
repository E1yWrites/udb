# Protocol family: `steelseries-mouse` (SteelSeries Rival, Sensei, Prime, Aerox mice)

Status: **detection only.** UDB recognises 56 SteelSeries mouse models (69
product IDs, all VID `1038`) and sends them nothing. The Arctis headset has its
own note: `docs/protocols/steelseries-arctis.md`.

The entries are generated by `npm run import:steelseries`.

## What OpenMouse's table shows

- **24 incompatible codec families.** `rival3`, `rival3-v2`, `rival-100`,
  `rival-110`, `rival-300`, `rival310`, `rival-600`, `rival650`, `rival-5`,
  `sensei-raw`, `sensei-310`, `sensei-ten`, `sensei-rival-pro`, `prime-plus`,
  `prime-mini`, `prime-mini-wireless`, `aerox3`, `aerox3-wireless`,
  `aerox3-wireless-gen2`, `aerox5`, `aerox5-wireless`, `aerox9-wireless`,
  `rival3-wireless` and `rival3-wireless-v2`. Command bytes, framing and value
  tables differ per family, and a family's commands sent to another's mouse
  would misprogram it. OpenMouse leaves out PIDs it could not trace to a
  public implementation.
- **No settings getter.** The table types `settingsReadable` as the literal
  `false` for every product: DPI, polling rate, lighting and buttons cannot be
  asked of the mouse. rivalcfg keeps a local JSON mirror for that reason.
- **Readable state is small.** 41 of the 69 products have a `10 00` firmware
  query. Battery can be read on some wireless mice (OpenMouse observed it on
  the Aerox 3 Wireless; its Rival 3 Wireless notes mention readable battery and
  firmware state).
- **Wireless models appear under several PIDs.** The cable, the 2.4 GHz dongle
  and sometimes a base station each enumerate separately. The importer gives
  each model one entry with one identity per PID.

## What was observed on hardware (OpenMouse, not UDB)

Only the Aerox 3 Wireless (`1038:183A` on the cable, `1038:1838` on the
dongle) is marked verified in OpenMouse's table. On macOS:

- The config channel is the usage page `FFC0`, usage `01` collection (interface
  3 on the cable); the dongle exposes the same collection.
- Every write is acked by a 64-byte input report that echoes the command byte
  and `00` (a third byte `01` on the dongle). The ack does not carry the
  setting's value.
- Over the dongle every command byte has `40` ORed in.
- Polling rate and DPI presets were checked physically (a rate meter, the DPI
  button cycling), not by reading.
- A DPI write replaces the on-device preset table with the written one.

For every other model the collection shape has not been captured; OpenMouse's
Rival 3 notes say its picker offers every interface and the firmware query is
what proves the right one was chosen.

## Why there is no adapter

- **Nothing can be read back.** Without a getter, no SteelSeries setting could
  reach `write-verified`. At most UDB could report "sent" (SPEC) or, for the
  Aerox 3 Wireless, "acknowledged", and an ack is not the value.
- **24 codecs and one captured shape.** An adapter per family is a lot of
  unverified code, and the one family with hardware notes still isn't checked
  by UDB.
- **Collections are unknown** for all but the Aerox 3 Wireless.
- **SteelSeries GG and Engine** hold the config interface open; the mouse does
  not answer while they run.

## What would unblock it

1. A device report (`Copy device report`) per family. It shows which
   collections declare which reports.
2. A decision on whether an ack counts as "accepted by the mouse" in the UI,
   distinct from both "sent" and "confirmed".
3. Then the Aerox 3 Wireless first: it is the only model with an observed
   channel and acks, though OpenMouse's evidence is not UDB's.
