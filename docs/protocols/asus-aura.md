# Protocol family: `asus-aura` (ROG and TUF keyboards and mice)

Status: **detection only.** UDB recognises 55 ASUS keyboard and mouse models
(73 product IDs, all VID `0B05`) and sends them nothing. The ROG Zephyrus G14's
built-in keyboard is lit through its standard LampArray collection instead
(`docs/protocols/lamparray.md`).

The registry entries are generated by `npm run import:aura` from the product
IDs in OpenRGB's tables.

## Aura is not one protocol

OpenRGB splits it into about ten sub-drivers, each with its own packets:
keyboards, TUF keyboards, mice (several generations), mousemats, monitors,
headset stands, AIO coolers, motherboards, addressable controllers and the ROG
Ally. The G14 and other laptops use a further dialect that OpenRGB doesn't list
(`19B6` is absent from its table).

UDB's registry covers mice, keyboards and headsets, so mousemats, monitors,
headset stands, coolers, motherboards and the Ally are not listed.

OpenRGB's tables reuse two PIDs: `189E` for both the Gladius II Wireless and the
Strix Impact II Gundam Edition, and `1979` for both the Spatha X 2.4 GHz dongle
and its dock (its mouse header also defines a fake dock PID, `FFFF`). The registry
lists each once, under the Gladius II Wireless and the Spatha X; the Gundam
Edition and the dock are not listed separately.

## What the sources show

**Desktop keyboards (OpenRGB `AsusAuraKeyboardController`).** Colours are
streamed as 65-byte output reports `00 C0 81 <count> 00`, then up to 15 LEDs
per packet as 4 bytes each, padded with `FF`. It then prepares a `00 C0 81 90`
buffer but only calls `hid_read` (its comment: "Read to apply"); that buffer is
never written. Nothing is read back. Most ROG and TUF keyboards use a separate controller
(`AsusAuraTUFKeyboardController`) that was not read for this note.

**Laptops (asusctl).** 64-byte packets, report ID `5D`; `SET` and `APPLY` are
17-byte packets:

| Bytes | Meaning |
|---|---|
| `5D B3 zone mode R G B speed direction 00 R2 G2 B2` | built-in effect |
| `5D B5` | SET |
| `5D B4` | APPLY |
| `5D BC …` | per-key frames (11 packets of 64 bytes) |

asusctl writes these and reads nothing back. Which of the G14's `FF31`
collections carries report `5D` is not established.

**Mice, mousemats and the rest.** Listed in OpenRGB with an interface number
and usage page (`FF01` for most mice, `FF13` for one Gladius II Wireless,
`0008` for the older Strix Evolve and Spatha). Their packets were not read.

## Why there is no adapter

- **Lighting only, and it can't be read back.** Both dialects stream colours
  and read nothing, so no Aura feature could reach `write-verified`. The colours
  are live, not settings stored on the device.
- **One adapter per sub-protocol.** ASUS devices can carry a firmware-update
  collection beside Aura (the G14 has `FF82:00CF`, "ASUS Component Firmware
  Update", which is denied there). Without a device report and captures per
  model, UDB can't tell which layout a model takes, and a wrong one would go to
  a device with that collection.
- **The collections are unknown.** OpenRGB picks interfaces by number; a
  browser needs usage pages and report IDs from a device report.
- **The G14 is already covered** by its LampArray collection, which is a
  standard with attribute read-back.

## Conflicts

Armoury Crate drives the same devices and overwrites any colours another tool
sends.

## What would unblock it

1. A device report (`Copy device report`) from a keyboard or mouse. It shows
   which collections declare which reports.
2. A decision about a send-only lighting path. LampArray already has one, so the
   write procedure supports it; what's missing is a model whose sub-protocol is
   settled.
3. For laptops: which `FF31` collection takes report `5D`, and whether it
   answers anything.
